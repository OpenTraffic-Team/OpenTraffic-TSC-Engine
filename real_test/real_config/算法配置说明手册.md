## 配置说明概述

### 什么是配置文件？

配置文件就像交通信号灯的"大脑设置"，告诉算法：

- 路口有哪些车道和相位
- 每个相位最少/最多亮多久
- 什么时候算"高峰期"
- 如何检测和处理"溢出"（车辆排队过长）

### 配置文件的格式

配置文件为 JSON 格式，修改前请备份原配置文件。

## 基础配置参数

### 1. `cur_inter_id` - 路口ID

**作用**：标识当前路口，必须与实际路口名称一致。
在真实联调中算法读取当前路口id通过

```json
"cur_inter_id": "XDJ_XCL"
```

- 必须与 Redis 中的路口ID完全一致
- 只能包含字母、数字和下划线

**调参建议**：
- 首次配置时，请确认路口ID与系统其他部分一致
- 如果路口ID错误，算法将无法读取数据

---

### 2. `lane_to_phase` - 车道到相位的映射

**通俗解释**：告诉系统"哪个车道的车走哪个相位"。

```json
"lane_to_phase": {
    "{intersection_id}_E_0": "EW_ES",
    "{intersection_id}_E_1": "EW_EN",
    "{intersection_id}_N_0": "NS_NE"
}
```

**参数说明**：

- **Key 格式**：`{路口ID}_{方向}_{车道编号}`
  - 方向：`E`（东）、`W`（西）、`N`（北）、`S`（南）
  - 车道编号：从路口中心向外，从 `0` 开始编号（按照实际雷视数据为准）
- **Value**：相位名称，如 `"EW_ES"` 表示"东向西直行，东向南左转"
- 单右转车道无需配置
- 不能有重复的车道编号

**调参建议**：
- 如果路口车道布局发生变化，需要同步更新此配置
- 不确定车道编号时，可以查看路口设计图纸或咨询技术人员

---

### 3. `phases` - 主相位列表

**通俗解释**：路口正常运行时使用的相位（不包括溢出相位）。

```json
"phases": [
    "WE_EW_ES_WN",
    "NS_SN_NE_SW"
]
```

- 至少需要 2 个相位
- 相位名称必须与 `stagePhase` 中的相位对应
- 不能为空数组

**调参建议**：
- 一般不需要修改，除非路口相位方案发生重大变化
- 修改时需要同步更新 `bind_phases` 和 `stagePhase`

---

### 4. `stagePhase` - 信号机相位映射

**通俗解释**：信号机上的相位编号对应的实际相位名称。

```json
"stagePhase": {
    "1": "WE_EW_ES_WN",
    "2": "NS_SN_NE_SW"
}
```

- 相位编号必须是字符串格式（如 `"1"` 而不是 `1`）
- 所有编号对应的相位必须在 `phases` 列表中
- 不能有重复的相位编号

**调参建议**：
- 必须与信号机实际配置完全一致
- 如果信号机相位编号改变，必须同步更新此配置

---

### 5. `bind_phases` - 绑定相位

**通俗解释**：哪些相位需要"绑定"在一起执行（通常用于4相位路口）。

```json
"bind_phases": [
    [0, 1],
    [2, 3]
]
```

**参数说明**：

- 数字 `0, 1, 2, 3` 对应 `phases` 列表中的相位顺序
- `[0, 1]` 表示第 0 和第 1 个相位绑定
- 例如：如果 `phases` 是 `["WE_EW", "WN_ES", "NS_SN", "NE_SW"]`，则：
  - `0` = `"WE_EW"`（东西直行）
  - `1` = `"WN_ES"`（东西左转）
  - `2` = `"NS_SN"`（南北直行）
  - `3` = `"NE_SW"`（南北左转）

**边界条件**：
- 所有数字必须小于 `phases` 数组的长度
- 不能有重复的数字
- 不能为空数组

**调参建议**：
- 4相位路口通常需要绑定，2相位路口通常不需要
- 如果不确定，可以设置为 `[[0], [1]]`（不绑定）

---

### 6. `layers_order_flag` - 绑定相位顺序执行标志

**通俗解释**：绑定的相位是否需要按顺序执行。

```json
"layers_order_flag": [false]
```

**参数说明**：

- `false`：绑定的相位可以灵活切换，不强制顺序
- `true`：绑定的相位必须按顺序执行
- 数组长度应与 `bind_phases` 的绑定组数一致
- 只能为 `true` 或 `false`

**调参建议**：
- 大多数情况下设置为 `false` 即可
- 只有在特殊路口设计需要严格顺序时才设为 `true`

---

## 时间控制参数

### 1. `phase_min_change_time` - 最短绿灯时间

**通俗解释**：每个相位最少要亮多少秒绿灯，保证车辆能安全通过。

```json
"phase_min_change_time": {
    "WE_EW_ES_WN": 20,
    "NS_SN_NE_SW": 20
}
```

**单位**：秒（s）

**边界条件**：
- 最小值：8秒（低于此值不安全）
- 最大值：60秒（超过此值影响通行效率）
- 推荐范围：15-30秒
- 不能为 0 或负数

**调参建议**：

| 路口情况 | 建议值 | 说明 |
|---------|-------|------|
| 小路口，车流量少 | 15-20秒 | 可以设置较短，提高通行效率 |
| 标准路口 | 20-25秒 | 平衡安全和效率 |
| 大路口，车流量大 | 25-30秒 | 需要更长时间保证安全通过 |
| 有大型车辆（货车、公交） | 25-30秒 | 大型车辆起步和通过需要更长时间 |

**常见问题**：

> **Q: 设置太短会怎样？**
> A: 车辆可能来不及通过，造成安全隐患，系统会自动限制最小值。

> **Q: 设置太长会怎样？**
> A: 其他方向等待时间过长，整体通行效率下降。

---

### 2. `phase_max_keep_time` - 最大绿灯时间

**通俗解释**：每个相位最多能亮多少秒绿灯，防止某个方向一直占着绿灯。

```json
"phase_max_keep_time": {
    "WE_EW_ES_WN": 65,
    "NS_SN_NE_SW": 65
}
```

**单位**：秒（s）

**边界条件**：
- 最小值：必须大于对应相位的最短绿灯时间
- 最大值：120秒（超过此值意义不大）
- 推荐范围：最短绿灯时间 × 2 到 × 4

**调参建议**：

| 路口情况 | 建议值 | 计算公式 |
|---------|-------|---------|
| 车流量均衡 | 最短绿灯 × 3 | 例如：20秒 × 3 = 60秒 |
| 某个方向车流量特别大 | 最短绿灯 × 4 | 例如：20秒 × 4 = 80秒 |
| 车流量较小 | 最短绿灯 × 2 | 例如：20秒 × 2 = 40秒 |

**常见问题**：

> **Q: 为什么需要最大绿灯时间？**
> A: 防止某个方向一直占着绿灯，导致其他方向长时间等待。

> **Q: 可以设置很大吗？**
> A: 不建议，超过 120 秒意义不大，且会影响其他方向的通行。

---

### 3. `phase_max_keep_num` - 最大保持周期数

**通俗解释**：当算法运行时间超过"所有相位最短绿灯时间之和 × 这个数字"时，系统会检查是否有相位还没执行。

```json
"phase_max_keep_num": 5
```

**边界条件**：
- 最小值：2
- 最大值：10
- 推荐值：5（一般不需要调整）

**调参建议**：
- 大多数情况下使用默认值 `5` 即可
- 如果路口相位较多（6个以上），可以适当增加到 6-7
- 如果路口相位较少（2个），可以适当减少到 3-4

> **注意**：此参数一般不需要调整，除非有特殊需求。

---

### 4. `delay_time` - 延迟时间

**通俗解释**：考虑数据采集和信号机响应的延迟时间。

```json
"delay_time": 1
```

**单位**：秒（s）

**边界条件**：
- 范围：0.5 - 3秒
- 推荐值：1秒

**调参建议**：
- 一般使用默认值 1秒 即可
- 如果系统延迟明显（数据采集慢），可以适当增加到 1.5-2秒
- 不建议频繁调整此参数

## 算法核心参数

### 1. `algo_version` - 算法版本

**通俗解释**：选择使用哪个版本的算法。

```json
"algo_version": "v1"
```

- 不能为空或拼写错误

**调参建议**：
- 推荐使用 `"v1"`（压力算法版本）
- 选择版本后，需要配置对应的版本参数（见下文）

---

### 2. `min_running_speed` - 最小行驶速度

**通俗解释**：用来区分车辆是"在行驶"还是"在等待"。速度低于这个值的车辆算作"等待车辆"。

```json
"min_running_speed": 10
```

**单位**：米/秒（m/s）  
**换算**：10 m/s ≈ 36 km/h

**边界条件**：
- 最小值：5 m/s（18 km/h）
- 最大值：15 m/s（54 km/h）
- 推荐范围：8-12 m/s

**调参建议**：

| 路口情况 | 建议值 | 说明 |
|---------|-------|------|
| 城市主干道 | 10-12 m/s | 车辆行驶速度较快 |
| 一般城市道路 | 8-10 m/s | 标准配置 |
| 学校、医院附近 | 6-8 m/s | 车辆行驶较慢，需要更敏感 |

**影响说明**：
- **增大此值**：系统认为更多车辆在"等待"，会加快红绿灯切换频率
- **减小此值**：系统认为更多车辆在"行驶"，会减慢红绿灯切换频率

**常见问题**：

> **Q: 为什么红绿灯切换太快？**
> A: 可能是 `min_running_speed` 设置太大，尝试减小 1-2 m/s。

> **Q: 为什么红绿灯切换太慢？**
> A: 可能是 `min_running_speed` 设置太小，尝试增大 1-2 m/s。

---

### 3. `debug` - 调试模式

**通俗解释**：是否开启详细日志输出。

```json
"debug": true
```

**可选值**：
- `true`：开启详细日志（用于排查问题）
- `false`：只记录关键日志（推荐生产环境）

**调参建议**：
- 生产环境推荐 `false`（减少日志量，提高性能）
- 调试问题时设为 `true`（可以看到更多细节）

## V1版本算法配置

### 1. `advanced_weight` - 算法权重

**通俗解释**：控制算法切换相位的"积极性"。数值越大，切换越慢，绿灯时间越长。

```json
"advanced_weight": 1
```

**边界条件**：
- 最小值：0.5
- 最大值：5.0
- 推荐范围：0.8 - 2.0

**调参建议**：

| 路口情况 | 建议值 | 效果 |
|---------|-------|------|
| 车流量变化快，需要快速响应 | 0.8-1.0 | 切换频率较快 |
| 标准路口，车流量稳定 | 1.0-1.5 | 平衡切换频率 |
| 车流量大，需要充分放行 | 1.5-2.0 | 切换频率较慢，绿灯时间更长 |

**影响说明**：
- **增大权重**：算法更"保守"，绿灯时间更长，切换频率降低
- **减小权重**：算法更"积极"，绿灯时间更短，切换频率提高

**常见问题**：

> **Q: 为什么某个方向总是等很久？**
> A: 可能是 `advanced_weight` 太大，尝试减小 0.2-0.5。

> **Q: 为什么红绿灯切换太频繁？**
> A: 可能是 `advanced_weight` 太小，尝试增大 0.2-0.5。

---

### 2. `phase_preference` - 相位优先级（可选）

**通俗解释**：如果希望某个方向的绿灯时间更长，可以设置更高的优先级。

```json
"phase_preference": {
    "0": 1,
    "1": 1.5
}
```

**参数说明**：
- Key `"0"`、`"1"` 对应 `bind_phases` 中的绑定组
- Value 是优先级系数，数值越大，该方向绿灯时间越长

**边界条件**：
- 优先级系数范围：0.5 - 2.0
- 默认值：1.0（所有方向平等）
- 不能为 0 或负数

**调参建议**：

| 场景 | 配置示例 | 说明 |
|-----|---------|------|
| 主路优先 | `{"0": 1.5, "1": 1.0}` | 主路方向（组0）绿灯时间更长 |
| 所有方向平等 | 不配置或全为 `1.0` | 默认情况 |
| 某个方向车流量特别大 | 该方向设为 1.3-1.5 | 给予更多通行时间 |

> **注意**：此参数为可选，大多数情况下不需要配置。

---

### 3. `morning_rush` - 早高峰时间

**通俗解释**：定义早高峰的时间段，在这个时间段内使用高峰期的参数。

```json
"morning_rush": ["07:00", "09:00"]
```

**格式说明**：
- 格式：`["开始时间", "结束时间"]`
- 时间格式：`"HH:MM"`（24小时制）
- 注意：冒号必须是英文冒号 `:`，不能是中文冒号 `：`

**边界条件**：
- 开始时间必须早于结束时间
- 时间格式必须正确（`"HH:MM"`）
- 不能跨天（如 `["22:00", "02:00"]` 不支持）

**调参建议**：
- 根据当地实际早高峰时间设置
- 一般早高峰为 `07:00-09:00` 或 `07:30-09:30`

---

### 4. `evening_rush` - 晚高峰时间

**通俗解释**：定义晚高峰的时间段。

```json
"evening_rush": ["17:00", "19:00"]
```

**调参建议**：
- 一般晚高峰为 `17:00-19:00` 或 `17:30-19:30`
- 根据当地实际晚高峰时间设置

---

### 5. `custom_peak_hours` - 自定义高峰时间

**通俗解释**：除了早高峰和晚高峰，还可以定义其他高峰时段（如中午高峰）。

```json
"custom_peak_hours": ["11:30", "13:30"]
```

**调参建议**：
- 如果路口有中午高峰，可以配置此参数
- 格式与早高峰、晚高峰相同

---

### 6. `phase_min_change_time_high_level` - 高峰期最短绿灯

**通俗解释**：高峰期时，每个相位的最短绿灯时间（通常比平时更长）。

```json
"phase_min_change_time_high_level": {
    "WE_EW_ES_WN": 25,
    "NS_SN_NE_SW": 25
}
```

**边界条件**：
- 必须大于或等于 `phase_min_change_time`（平时最短绿灯）
- 推荐范围：平时最短绿灯 + 5-10秒

**调参建议**：

| 路口情况 | 建议值 | 说明 |
|---------|-------|------|
| 车流量特别大 | 平时最短 + 10秒 | 例如：平时20秒 → 高峰期30秒 |
| 标准高峰期 | 平时最短 + 5秒 | 例如：平时20秒 → 高峰期25秒 |
| 高峰期不明显 | 与平时相同 | 不单独配置，使用平时值 |

---

### 7. `phase_min_change_time_high_morning_level` - 早高峰最短绿灯

**通俗解释**：早高峰专用的最短绿灯时间（如果与晚高峰不同）。

```json
"phase_min_change_time_high_morning_level": {
    "WE_EW_ES_WN": 25,
    "NS_SN_NE_SW": 25
}
```

**调参建议**：
- 如果早高峰和晚高峰车流特点不同，可以分别配置
- 大多数情况下，早高峰和晚高峰使用相同的值即可

---

### 8. `phase_min_change_time_high_evening_level` - 晚高峰最短绿灯

**通俗解释**：晚高峰专用的最短绿灯时间。

```json
"phase_min_change_time_high_evening_level": {
    "WE_EW_ES_WN": 25,
    "NS_SN_NE_SW": 25
}
```

**调参建议**：
- 与早高峰配置类似
- 如果早高峰和晚高峰相同，可以不配置，使用 `phase_min_change_time_high_level`

---

### 9. `high_level_weight_minspeed` - 高峰期算法权重和速度

**通俗解释**：高峰期时，算法的权重和速度判断阈值。

```json
"high_level_weight_minspeed": [2.5, 10]
```

**参数说明**：
1. `[0]` - **高峰期权重**：类似 `advanced_weight`，控制高峰期切换频率
2. `[1]` - **高峰期速度阈值**：类似 `min_running_speed`，高峰期时的速度判断

**边界条件**：

| 参数 | 最小值 | 最大值 | 推荐值 |
|-----|-------|-------|-------|
| 高峰期权重 | 1.5 | 4.0 | 2.0-3.0 |
| 高峰期速度阈值 | 6 | 12 | 8-10 |

**调参建议**：

| 路口情况 | 建议配置 | 说明 |
|---------|---------|------|
| 高峰期车流量特别大 | `[3.0, 10]` | 权重更大，切换更慢 |
| 标准高峰期 | `[2.5, 10]` | 标准配置 |
| 高峰期需要快速响应 | `[2.0, 8]` | 权重更小，切换更快 |

---

### 10. `max_keep_time_high_level` - 高峰期最大绿灯

**通俗解释**：高峰期时，每个相位的最大绿灯时间。

```json
"max_keep_time_high_level": 80
```

**边界条件**：
- 必须大于高峰期最短绿灯时间
- 推荐范围：高峰期最短绿灯 × 3 到 × 4

**调参建议**：
- 一般设置为高峰期最短绿灯的 3-4 倍
- 例如：高峰期最短绿灯 25秒 → 最大绿灯 75-100秒

## V2版本算法配置

### 1. `trained_rl_model_phase` - 模型相位

**通俗解释**：强化学习模型训练时使用的相位列表。

```json
"trained_rl_model_phase": ["WE_EW_ES_WN", "NS_SN_NE_SW"]
```

**调参建议**：
- 必须与训练模型时使用的相位完全一致
- 不得随意修改，否则模型无法正常运行

---

### 2. `model_path` - 模型文件路径

```json
"model_path": "/path/to/model/file"
```

**调参建议**：
- 确保路径存在且文件可读
- 使用绝对路径，避免相对路径引起问题

## 溢出处理配置

### 什么是"溢出"？

当某个方向的车辆排队太长，一直排到路口中心，就会"溢出"。溢出会导致：

- 车辆无法正常通行
- 可能影响其他方向的车辆
- 造成交通拥堵

**溢出检测原理**：系统通过检测路口出口方向的车辆情况来判断是否溢出：

1. **检测条件1**：速度为 0 的车辆数量达到阈值
2. **检测条件2**：低速且距离路口近的车辆数量达到阈值
3. **检测条件3**：放宽条件（防止设备误差导致误判）

---

### 1. `overflow_phase_to_road` - 溢出相位映射

**通俗解释**：当某个方向发生溢出时，可以使用哪些"溢出相位"来缓解。

```json
"overflow_phase_to_road": {
    "WE_EW_WN_ES": [],
    "NS_SN_NE_SW": [],
    "WE_WN": ["S", "W_S"],
    "EW_ES": ["N", "E_N"]
}
```

**参数说明**：
- **Key**：溢出相位名称（如 `"WE_WN"` 表示"西向北"）
- **Value**：数组，表示哪些方向发生溢出时可以使用这个相位
  - `"S"`：南口溢出
  - `"W_S"`：西口和南口同时溢出
  - `"N"`：北口溢出
  - `"E_N"`：东口和北口同时溢出

**配置逻辑**：

1. 找出容易溢出的方向：观察路口，哪些方向经常排队？
2. 找出可以缓解的相位：哪些相位可以让溢出方向的车辆通过？
3. 建立映射关系：当方向A溢出时，使用相位B

**配置示例详解**：

```json
"WE_WN": ["S", "W_S"]
```

含义：当南口或西口和南口同时发生溢出时，可以使用**"西向北"**这个相位来缓解。

**调参建议**：

| 路口情况 | 配置策略 | 示例 |
|---------|---------|------|
| 某个方向经常溢出 | 为该方向配置专门的溢出相位 | 南口常溢出 → 配置 `"WE_WN": ["S"]` |
| 多个方向可能同时溢出 | 配置组合溢出 | `"WE_WN": ["S", "W_S"]` |
| 没有溢出问题 | 可以不配置（留空数组） | `"WE_EW_WN_ES": []` |

> **重要提示**：
> - 溢出相位配置需要根据实际路口情况设计
> - 建议先观察路口 1-2 周，找出容易溢出的方向
> - 不确定时可以咨询技术人员

### 2. `min_overflow_dis_speed` - 溢出检测阈值

**通俗解释**：系统判断"溢出"的四个条件参数。

```json
"min_overflow_dis_speed": [8, 110, 40, 2.78]
```

**参数说明（按顺序）**：

1. `[0]` - **零速车辆数阈值**：速度为 0 的车辆达到多少辆算溢出
2. `[1]` - **零速检测距离**：检测零速车辆的距离范围（米）
3. `[2]` - **低速检测距离**：检测低速车辆的距离范围（米）
4. `[3]` - **低速阈值**：速度低于多少（米/秒）算低速车辆

**边界条件**：

| 参数 | 最小值 | 最大值 | 推荐值 |
|-----|-------|-------|-------|
| 零速车辆数 | 3 | 15 | 5-8 |
| 零速检测距离 | 50 | 150 | 80-110 |
| 低速检测距离 | 20 | 60 | 30-45 |
| 低速阈值 | 1.0 | 5.0 | 2.0-3.0 |

**调参建议**：

| 路口情况 | 建议配置 | 说明 |
|---------|---------|------|
| 大路口，车道多 | `[8, 110, 40, 2.78]` | 需要更多车辆才判定溢出 |
| 标准路口 | `[5, 80, 35, 2.5]` | 标准配置 |
| 小路口，容易溢出 | `[3, 60, 30, 2.0]` | 更敏感，提前检测溢出 |

**影响说明**：
- **增大零速车辆数阈值**：需要更多静止车辆才判定溢出（更不敏感）
- **减小零速车辆数阈值**：更少的静止车辆就判定溢出（更敏感）
- **增大检测距离**：检测范围更大，可能误判
- **减小检测距离**：检测范围更小，可能漏判

**常见问题**：

> **Q: 为什么明明溢出了，系统没检测到？**
> A: 可能是阈值设置太大，尝试减小零速车辆数阈值 1-2。

> **Q: 为什么没溢出，系统却判定溢出了？**
> A: 可能是阈值设置太小，尝试增大零速车辆数阈值 1-2。

### 3. `min_overflow_dis_speed_relax` - 溢出放宽条件

**通俗解释**：为了防止设备误差导致误判，系统还有一个"放宽条件"。只要满足这个条件，即使不满足前面的条件，也会判定为溢出。

```json
"min_overflow_dis_speed_relax": [50, 4.1]
```

**参数说明**：

1. `[0]` - **放宽检测距离**：检测距离（米）
2. `[1]` - **放宽速度阈值**：速度低于多少（米/秒）

**边界条件**：

| 参数 | 最小值 | 最大值 | 推荐值 |
|-----|-------|-------|-------|
| 放宽检测距离 | 30 | 80 | 45-60 |
| 放宽速度阈值 | 2.0 | 6.0 | 3.5-5.0 |

**调参建议**：
- 一般使用默认值即可
- 如果设备精度不高，可以适当增大检测距离和速度阈值
- 不建议频繁调整此参数

---

### 4. `overflow_vehicle_count` - 溢出车辆数阈值

**通俗解释**：在放宽条件下，需要多少辆满足条件的车辆才判定为溢出。

```json
"overflow_vehicle_count": 3
```

**边界条件**：
- 最小值：2
- 最大值：10
- 推荐值：3-5

**调参建议**：
- 标准路口使用 `3`
- 大路口可以适当增加到 4-5
- 小路口可以适当减少到 `2`

---

### 5. `overflow_times` - 溢出持续次数

**通俗解释**：溢出状态需要持续多少次检测才真正触发溢出处理（防止误判）。

```json
"overflow_times": 5
```

**边界条件**：
- 最小值：3
- 最大值：10
- 推荐值：5

**调参建议**：
- 大多数情况下使用 `5` 即可
- 如果路口容易误判，可以适当增加到 6-7
- 如果需要快速响应，可以适当减少到 3-4

**影响说明**：
- **增大此值**：需要更长时间的溢出才触发处理（更保守，减少误判）
- **减小此值**：更短时间的溢出就触发处理（更敏感，快速响应）

## 调参建议与常见问题

### 调参流程建议

1. **观察路口情况（1-2周）**
   - 记录哪些方向容易拥堵
   - 记录高峰时段
   - 记录是否有溢出问题

2. **基础参数配置**
   - 确认路口ID、相位映射正确
   - 设置合理的最短/最长绿灯时间

3. **算法参数调优**
   - 根据车流量调整 `advanced_weight` 或 `min_running_speed`
   - 配置高峰时段参数

4. **溢出参数配置（如有需要）**
   - 观察溢出情况
   - 配置溢出相位映射
   - 调整溢出检测阈值

5. **验证和优化**
   - 观察调整后的效果
   - 根据实际情况微调参数
   - 记录有效配置

---

### 常见问题排查

#### 问题1：红绿灯切换太快

**可能原因**：
- `min_running_speed` 太大
- `advanced_weight` 太小（V1版本）

**解决方法**：
- 减小 `min_running_speed` 1-2 m/s
- 增大 `advanced_weight` 0.2-0.5（V1版本）

---

#### 问题2：红绿灯切换太慢

**可能原因**：
- `min_running_speed` 太小
- `advanced_weight` 太大（V1版本）

**解决方法**：
- 增大 `min_running_speed` 1-2 m/s
- 减小 `advanced_weight` 0.2-0.5（V1版本）

---

#### 问题3：某个方向等待时间过长

**可能原因**：
- 该方向的最短绿灯时间太短
- `phase_preference` 优先级太低（V1版本）

**解决方法**：
- 适当增加该方向的最短绿灯时间 5-10秒
- 提高该方向的 `phase_preference` 优先级（V1版本）

---

#### 问题4：溢出检测不准确

**可能原因**：
- `min_overflow_dis_speed` 阈值设置不当
- `overflow_times` 设置不当

**解决方法**：
- 如果漏检：减小零速车辆数阈值 1-2，或减小 `overflow_times` 1-2
- 如果误检：增大零速车辆数阈值 1-2，或增大 `overflow_times` 1-2

---

#### 问题5：高峰期效果不好

**可能原因**：
- 高峰时段配置不正确
- 高峰期参数设置不当

**解决方法**：
- 检查 `morning_rush` 和 `evening_rush` 时间是否正确
- 适当增加高峰期最短绿灯时间
- 调整 `high_level_weight_minspeed` 参数

---

### 参数调整注意事项

1. **一次只调整一个参数**：便于观察效果，便于回滚
2. **调整幅度要小**：建议每次调整 10-20%，不要一次性大幅调整
3. **记录调整历史**：记录每次调整的参数和效果，便于后续参考
4. **观察周期要足够**：至少观察 1-2 天，高峰时段和平时都要观察
5. **备份原配置**：调整前备份原配置文件，如果效果不好可以快速恢复
